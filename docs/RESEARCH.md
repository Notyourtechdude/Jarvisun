The Qwen3.5 repository currently covers Qwen3.5, Qwen3.6, and Qwen3.8; its current heading is Qwen3.8. Consequently, the older Qwen3-8B default is a compatibility baseline, not the latest generation. Repository branches can change; record an immutable model revision and weight checksum when acquiring a chosen model. The exact newer cards, quantized-file sizes, gating, and license text could not be confirmed because this environment's HTTPS proxy rejected Hugging Face with `403 Forbidden` during CONNECT. Google Gemma and Mistral model API lookups were likewise inaccessible, so they are not presented as verified candidates.

A rough weight-only lower bound at four bits per parameter is 0.5 bytes/parameter: 4B ≈ 2 GB, 8B ≈ 4 GB, 9B ≈ 4.5 GB, 27B ≈ 13.5 GB in decimal units. This arithmetic is not an artifact download size or RAM/VRAM recommendation. Quantization metadata, unquantized layers, vision encoders/projectors, KV cache, context length, concurrency, and runtime allocation add memory. BF16 weight-only arithmetic is approximately 2 bytes/parameter. Active MoE parameter counts do not mean only active expert weights must fit in memory.

Start by discovering the owner's available CPU, RAM, GPU/unified memory and required tasks. Try a small instruct model for text; evaluate a compatible 4B/9B multimodal candidate only after its weight license and server support are confirmed. Compare on a fixed local task set: cited document answers, abstention when evidence is missing, tool proposals under denials, image grounding, coding checks, time to first response, end-to-end latency, and peak memory. Evaluate quantizations separately. Published scores alone do not establish the best model for this personal agent.

## Serving and interoperability

The [official Qwen3 README](https://github.com/QwenLM/Qwen3/blob/main/README.md) explicitly documents Ollama `qwen3:8b` with the OpenAI-compatible `http://localhost:11434/v1/` route. [Ollama's actual compatibility implementation](https://github.com/ollama/ollama/blob/main/openai/openai.go) was read to check request/response conversion. The standalone Ollama documentation site was blocked by the proxy; guessed older documentation-file paths returned 404 and were not treated as evidence.

The [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) documents `/v1/models`, `/v1/chat/completions`, model aliases, generation limits, and multimodal OpenAI-compatible requests. Its [multimodal documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md) describes vision/projector requirements. Compatibility is partial and model/template dependent. These sources support the protocol choice, not a claim that any candidate has been loaded successfully here.

## Codex, OAuth, and application sign-in

The [current official Codex README](https://github.com/openai/codex/blob/main/README.md#using-codex-with-your-chatgpt-plan), fetched successfully, explicitly supports **Sign in with ChatGPT** in the official Codex CLI for eligible Plus, Pro, Business, Edu, or Enterprise plans, and separately describes API-key authentication. The official [authentication documentation pointer](https://github.com/openai/codex/blob/main/docs/authentication.md) now directs to [developers.openai.com/codex/auth](https://developers.openai.com/codex/auth). Fetching that destination was blocked by a proxy CONNECT 403, so its current detailed policy text was not reviewed.

The official [interactive-login implementation](https://github.com/openai/codex/blob/main/codex-rs/login/src/server.rs) and [device-code implementation](https://github.com/openai/codex/blob/main/codex-rs/login/src/device_code_auth.rs) were read. They establish that supported Codex authentication includes an OAuth authorization flow with a loopback callback and device-code machinery. This is evidence for sign-in inside Codex; it does not establish an unrestricted third-party OAuth client or permission to reuse Codex/ChatGPT subscription tokens against a general chat-completions endpoint.

The [official Codex app-server README](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md), also fetched, documents account/routing and integration-specific behavior. Jarvis implements a disabled-by-default official CLI adapter with an explicit owner executable and separate private authentication home; see [CODEX.md](CODEX.md) for verified flags, use, and trust limits. Controlled subprocess tests passed; real owner login/subscription inference was not run. The adapter does not extract tokens, read another application's auth files, reuse browser cookies, or establish general subscription-funded API access.

Jarvis's owner sign-in protects Jarvis data and actions. An optional external identity/OIDC login could authenticate the owner but would not authorize a model provider or confer inference credits. General cloud inference in this baseline uses an explicitly configured provider API key over HTTPS. A universal “sign in to any AI subscription and use its inference API” feature is not supported by the consulted evidence.
